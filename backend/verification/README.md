# verification —— 让仿真输出变得**可判定**的装置

这个目录不属于上游 MiroFish。它是这个 fork 加的东西，回答的是一个上游没回答的问题：

> MiroFish 能演出一份**很像结论**的报告，**但它没有任何机制告诉你：这一次跑出来的
> 东西可不可信。**

这里放的**不是**「一套让仿真更准的方法」，也不是「一套测试」。它是一组
**运行时守卫**加一组**离线复现**：守卫能在你不该相信的时候让你别信（说不出来
就明说说不出来），复现能让你亲手把每一个结论跑出来看。

---

## 装与跑

```bash
cd backend
python -V                            # 先看这一行：装置装得上 3.10 / 3.11，装不上 3.12（见下）
pip install -r requirements.txt      # 装置依赖的 camel / oasis 也在里面
pip install pytest                   # 装置自带的测试要它 —— 它不在 requirements.txt 里
python -m verification.run_all
```

> ⚠️ **Python 的解释器版本有下界也有上界：装得上的是 3.10 与 3.11，3.12 装不上。**
> 这条不是我们设的，是上游依赖在包元数据里设的 —— 卡住的是
> **`camel-oasis==0.2.5`，它写着 `Requires-Python: >=3.10.0,<3.12`**
> （`camel-ai 0.2.78` 是 `<3.13,>=3.10`，比它松）。四个直接相关的包取交集，
> 得到的就是 **3.10 / 3.11 两个小版本**。
>
> **在 3.12 上，失败的样子会把人带偏。** `pip install -r requirements.txt` 停在解析那一步，
> 报的是 `ERROR: Could not find a version that satisfies the requirement camel-oasis==0.2.5`
> —— 它**不说**「是你的 Python 太新」，只说「找不到」。读起来像是包名打错了、
> 或者 PyPI 挂了、或者网络不通，于是人就去查网络。**实际原因只有一个：解释器版本。**
>
> **这个界会跟着上游漂**（上游放宽了，这里就该改），所以它**只写在这一处**，
> 并且配了一条现场对账：`test_readme_claims.py` 会把上面这串
> `Requires-Python: >=3.10.0,<3.12` 拿去和现场装着的 `camel-oasis` 元数据逐字比一次，
> 同时复核「它确实把 3.12 排除在外、而 `camel-ai` 确实比它松」——
> 也就是说，「3.12 装不上、卡住的是 camel-oasis」这句话**是每次跑测试都重验一遍的**，
> 不是写完就算。（跟下面 `mcp<2` 那条上界是同一类东西：
> **依赖自己声明得不对，pip 不会拦你，只会在装完之后炸给你看。**）

**不要 API key、不要 Zep、不发 LLM 请求、不花钱。** 机器闲着时本机实测 **37.1 / 37.8 /
37.8 秒**跑完（其中一部分是最后那步**对账**）。

> ⚠️ **这个秒数是「机器闲着的时候」的数，别拿它当刻度。** 同一台机器、同一份代码，
> 实测在 **37 ~ 86 秒**之间浮动 —— 取决于当时机器多忙。**跑得慢不代表装置有问题**，
> 装置自己也**不计时、不落盘耗时** —— 报告里没有秒数这一栏。这一条特意写出来，
> 是因为「我这儿怎么跑了 80 秒」是照 README 走一遍的人最容易先怀疑自己的地方。

> ⚠️ **一处例外，免得把「离线」读大了：分词器要一份数据文件。** 装置用的
> `OpenAITokenCounter` 走 tiktoken，而 tiktoken 的编码表是首次使用时下的静态数据
> （**本机实测落盘 3,613,922 字节 ≈ 3.6 MB** —— 这是**观测值不是常数**：大小与编码名
> 都随 `tiktoken` 版本变；同一节的 `o200k_base` / `n_vocab=200019` 也是**现场取值**，
> 报告的环境一节会记下来）。**缓存热了，一个网络请求都不发** ——
> 说「0.000 秒」是指**网络这一侧**：进程里第一次取编码器仍要 **0.7 秒**
> （解析本地那 3.6 MB 的表，不走网），同一进程里再取才是 0.000 秒。
> **冷缓存时要下这一次** —— 这是个**观测量、不是常数**，
> 取决于网络：本机两次分别量到 **3.5 秒**和 **6.5 秒**。所以准确的说法是
> 「**不发 LLM 请求、不调 API**」，不是「这台机器上不需要任何网络」。
> 这条不能含糊 —— 切片那一节的数字（270 条 / 5130 token）**全依赖这个分词器**，
> 换个计数方式就不是这些数了。报告的**环境**一节会把编码名、缓存目录和
> **这份表的实测字节数**（`tokenizer_cache_bytes`）记下来。
>
> 这个「3.6 MB」是**会随 `tiktoken` 版本漂的量**，所以它住在**四处**：本节开头
> 那行正文、《开源及第三方资源使用清单》里**两处**（第二节那张表，以及任务清单里
> 已勾掉的那条「量出编码表落盘字节数」）、以及 `run_all` 产物里现场量出来的那个
> 字段（`tokenizer_cache_bytes`）—— **四处都有检查**（`test_docs_claims.py`：
> 两份材料里的几处必须相等；产物在盘上时，还要跟产物里那个读数对得上）。
> 别处要提它，一律只说「一张几 MB 的静态表」。
>
> ⚠️ **这条检查原先只盖住三处，第四处是补上的。** 它按「落盘 … 字节」这个形状去抓，
> 而清单的任务清单那条写的是「量出编码表落盘字节数（那个数 `B`）」—— 数字后面跟的是
> `B）`，那个形状匹配不上，于是那一处**一条检查都没有**，而正文写着「三处被测试互相钉住」。
> 这正是下面那句话的反面：**号称几处、就得真的几处**。现在那个正则认两种写法。
>
> 换句话说，规矩不是「只写一处」，而是「**写几处、就得有几条检查**」；真要引数，
> 引产物里那个。（反面教材是下面「守卫自己的测试」里那句「**这个条数只写在这一处**」：
> 会漂的数字抄第二遍、**又没有检查**，就一定会腐烂。）
>
> （`tiktoken` 是**自己钉的**：`requirements.txt` 里 `tiktoken==0.7.0`。它原先只随
> `camel-ai` 的传递依赖进来 —— 那样「锁的版本」和「装的版本」是两件事，而整张引文表
> 的 token 数全挂在这个分词器上。`run_all.py` 量环境时直接 `import tiktoken`。）

预期看到：三条复现各自打印它量到的数，接着一步**对账**，结尾一张汇总，退出码 `0`。
退出码有三种，见下。

跑完会在当前目录落下两个文件（已 gitignore）：

```
verification_report.md    给人看的：汇总 + 环境 + 三条的原样转录 + 对账
verification_report.json  同一份内容的结构化版本
```

```bash
python -m verification.run_all --out /tmp/rep    # 换个落点
python -m verification.run_all --no-report       # 只看屏幕，不落文件
```

报告里每一条的正文，就是那条命令**当时打在屏幕上的原话**，逐字转录 ——
**不做二次解析**。这是刻意的：报告里的数字如果是「再算一遍」来的，就可能和
产生它的那次运行对不上，而这份报告的全部意义就是「我看到的和它说的是同一件事」。
报告另附一节**环境**（Python、平台、camel/oasis 版本、现场量到的时钟步长、
工作目录），也就是「这批数字是用什么跑的」的凭据。

汇总里**不出现通过率** —— 理由见下。

### 只想跑一条

```bash
python -m verification.repro_01_slicing        # 切片正反馈环
python -m verification.repro_02_timestamp      # 同拍碰撞
python -m verification.repro_03_concurrency    # 并发次序（边界，不修）
```

### 不用 API key，那测的到底是什么（**这段请务必读完再信上面的结论**）

「不要 key」很容易被读成「没真跑，是拿假东西糊的」。这里说清楚测到了哪一层。

两个缺陷都不在模型上，在**写入记忆的决策**上：一条消息该不该切、几条记录的时间戳
谁在前。要碰到这两处，只需要一个**真的 `ChatAgent` 对象和它真的记忆**，不需要它
有模型。所以探针的做法是：

```python
agent = ChatAgent.__new__(ChatAgent)     # 绕开 __init__：不构造模型后端
agent.memory = ...                       # 塞一个真的 ScoreBasedContextCreator
```

**哪些是真的：** `ChatAgent` 这个类、它依次调用的方法体（`update_memory`、
`_record_tool_calling` 及它们调用的全部逻辑）、`Memory`、`ScoreBasedContextCreator`、
真的分词器、真的驱逐算法。判据也是真的 —— 它拿的是 `memory.get_context()` 返回的
**那串真消息**，直接过 API 的同一条校验规则。

**哪些是假的：** 没有模型后端（不产生 token、不花钱），② 那一节把 `time.time_ns`
换成一张手推的表（冻钟，见下）。

**所以本装置能声称的：** 「这两个函数在**给定的输入下**会这样」。这是函数级的事实，
换台机器也成立。
**不能声称的：** 「一整局仿真跑出来会怎样」—— 那要**真 LLM 在环**，本装置没有。
（替身模型能把一整局**跑完**、能把守卫的两个分支都走到 —— 但替身不产生真实行为，
所以它证不了这一条。见「端到端：替身模型跑一整局」。）

> 冻钟那一段值得单说：真实时钟下「同不同拍」由调度决定，是**概率性**的（实测
> 多数同拍、偶尔跨拍）。把钟冻住就让它**每次都同拍**，于是每次复现。冻住的只是
> 「同拍」这个前提，不是结论 —— 结论仍然是排序键在相等处按分数把后写的排到前面，
> 那是源码里读得出来的。

### 守卫自己的测试

```bash
python -m pytest verification/tests -q         # 当前 254 条，十来秒
```

> **刚 clone 下来第一次跑，屏幕上会是 `251 passed, 3 skipped`。** 跳掉的三条里，
> 两条要 **本机产物**，而产物**不入库**（每次跑重新生成）：一条问的是
> 「裁决产物有没有过期」，它要的是 `verification_report.json`；另一条把 README 里
> 那三个数（`run_all 3/3` 等）拿去和**本机产物**对 —— 同样没得对。跑一次
> `python -m verification.run_all`、`adjudicate`、`selfproof`，它们就有了，第二次跑就是满的。
> **那不是挂了两条，也不是你装错了**：这两条本来就是「没条件判」，不是「判不过」
> （理由见下文「产物过期」那一节）。
>
> **第三条与产物无关，是平台**：`test_a_signal_killed_repro_is_not_measured` 要的是
> 「被信号杀死的子进程返回负值」，而 Windows 上 `wait()` 不给负值（`kill` 给的是 `1`，
> 那一处 `_probe.py` 已声明过），所以它在 Windows 上恒跳、在 Linux 上照跑。
> **所以在 Linux 上第一次跑是 `252 passed, 2 skipped`。** 这一条跳的是「这台机器上
> 量不出那个值」，和上面两条跳的理由不同、也不是同一类话。
>
> 这句话是**实测**的，不是推的：拿 `git clone` 出来的仓库，再把工作区里**受版本
> 控制的那批文件**照原样盖回去（也就是「提交完再 clone」的样子），跑出来是
> `251 passed, 3 skipped`、**一条红都没有**。它此前有一处是**错的**、一处只是
> **过期**：先写的是 `243 passed, 1 skipped`，而实跑会红一条 —— 那条核数字的
> 测试**没有前提门**，
> 产物不在时抛的是 `FileNotFoundError` 的 traceback（见下文那一段）；改成
> `243 passed, 2 skipped` 之后，**条数涨了、跳的也涨了一条**（就是上面那条平台性的），
> 而这一句没人跟着改。**一句写着「实测」的话，量它的那次和读它的这次不是同一次** ——
> 下面那句「只写在这一处」既是纪律，也是这条第二次腐烂的原因。

> ⚠️ **这个条数只写在这一处。** 加测试之后**只改这里**，别在别的章节再抄一遍 ——
> 抄了就一定会腐烂：实测有一次只同步了一处，另外两处停在旧数字上，
> 而**照 README 跑一遍的人立刻会看出对不上**（屏幕上打着的是真实条数）。
>
> 这条规矩现在**有东西兜着**：`tests/test_readme_claims.py` 会把这一行里的数字
> 和 `pytest --collect-only` 数出来的真实条数对一遍 —— 加了用例却忘了改这里，
> 它会当场红，而不是等它漂到你面前。

**只需要 camel**，不需要 flask / zep / API key（上游 `backend/tests/` 里那些要完整
后端才收集得动，所以这两套是分开的）。

| `test_reconcile_evidence.py` | **对账自检的产物还在、还没过期**（见下） |
| `test_readme_claims.py` | **这份 README 里写死的数目**（用例条数）和现场对得上 —— 免得它像上面那个「154」一样悄悄腐烂 |

| `test_environment_pins.py` | **照 README 装出来的环境就是装置量的那个环境**：两个仿真内核与 `tiktoken` 锁的版本 == 装的版本（整张引文表挂在这上面）、`mcp<2` 这条上界还在、那个真会炸的导入真的没炸、**清单第二节那张表的版本号**也逐格和现场比 —— 配一条**阴性对照**（把 2.x 的条件造出来）证明它不是恒绿的 |
| `test_upstream_baseline.py` | **我们基于哪个上游版本**：六处写的是同一个 commit（抄歪一处就红）、那个 commit 真在仓库里且是 `HEAD` 的祖先 —— 配两条阴性对照证明它不恒真（一条拿不存在的串去问，一条拿「没有 `.git` 的目录」去问）；**浅克隆、以及「这里根本不是仓库」，只在「查出来是阴性」时才跳过**（阳性直接采信）。**另管仓库根那两张「对上游的改动」表**：`NOTICE` 那张必须**等于**对基线 diff 出来的全部上游改动文件（**一个不多一个不少**），且它的数目必须和《开源及第三方资源使用清单》那张**逐项一致** —— **同一张表的两份副本，早先只有一份有人核**，另一份少列了 `backend/requirements.txt` 也没人知道。**还有那一栏「最后改动」的日期**：逐条拿去问 `git log -1 --date=short`（AGPL-3.0 §5(a) 要的是「日期」，不是「一个范围」），配一条阴性对照证明这不是恒绿的 |

> **「这里没有历史可查」和「历史被人改过」是两件事，别报成一个。**
> 上面那条祖先检查原先把「`git` 返回非零」一律当成「这个对象不在」——于是在一份
> **没有 `.git` 的副本**里（从 GitHub 点「Download ZIP」就是），它会红，而红上写的
> 指控是「**要么串打错了，要么这个 fork 的历史被人重写过**」。
> 真正的原因（这里根本没有历史可查）**不但没说出口，还被换成了一个更重的指控** ——
> 比不报还坏：**没条件判 ≠ 判不过**，而报错的原因还是错的。
> 同一件事在 `test_docs_claims.py` 那一侧**本来就是跳过的**（三个检查都说「无从对 diff」），
> **同一套纪律，一个地方执行了、另一个地方没有**。
> 现在两侧都先问一句「这里到底是不是 git 仓库」（`_is_repo()`），不是就**跳过并写清为什么**；
> 另配一条阴性对照：本仓必须答「是」、一个不在任何仓库里的空目录必须答「否」——
> **两个方向都堵住**（恒真就退回那条错指控，恒假则本仓里这条检查再也不跑）。

#### 守卫：两个方向都要成立

该拦的拦（消息自己放得下 → 整条写入）、**该切的不切**（消息自己就超上限 → 原样
交回，不许为了「修好切片」把它整条塞进去）。后面这个方向是必需的 —— 少了它，
一个「一律不切」的实现会让切片事故的测试全绿。

守卫怎么测到的：`install(target=…)` 这个注入口传一个**替身类**进去，
所以这些测试**不去改真的 `ChatAgent`**、不发 LLM。

> 这套测试**验过它不是恒真的**：把守卫的判据分别改坏七处（`>` 写成 `>=`、
> 变成空操作、变成「一律不切」、`STEP` 调到比 camel 的 `1e-6` 还细、时间戳

#### 判词：不许和同一行的读数打架

这条是被一次**真实的翻车**逼出来的。第三节那张表的「后果」一列原来是写死的，
于是有过一次运行一边打出 `3.35 ms / 9.66 拍`、一边宣称「同拍 → 碰撞才发生」——
同一张表里读数和结论互相打脸。

**这类错不会自己报错**：装置照样退出 0、汇总照样 3/3，只有人一行行看才发现。
所以判定改成由读数算（`_tick_verdict`），并把这个不变式写成断言：

> 表里说「同拍」，那一行的 `gap` 就必须真的小于 `tick`；反之亦然。

测试在一整片 `(gap, tick)` 网格上扫这条，**两种预期方向都扫**（缺陷行预期跨拍、
修好行预期同拍）—— 写死的那版正是在「与预期相反」那条走法下露的馅。
它与预期不符时**直书「与预期相反」**，不许悄悄折回预期那一侧。

> 这套也**验过它不是恒真的**：三处变异（判词写死、`<` 写成 `<=`、去掉

>

> 于是按实测改了 —— 对不上的是那个数字（当时多半是从第一处抄下来的），
> **不是论断**：三处变异都让测试红了，这一点两条数字下都成立。

#### 引文：文档里的行号不许腐烂

`test_citations.py` 管**两件不同的事**，所以它有两半：

> （在这个分词器下恰好量出 12），不是代码里的常数。**数值上对、引文上错**，而当时
> 没有任何东西会因此变红。这就是下半第一条规则：那个写法不许在材料里留下第二份。
>
> （**那个写错的字面量在这份 README 里就不再抄一遍了** —— 抄一遍，下面那个扫描
> 就会连这份 README 一起红。要看原文，去 `tests/test_citations.py` 里那条规则，
> 它是被扫描排除在外的。）
>
> 两半都**验过不是恒真的**。上半：五处变异（行号错开一格、引越界的行号、换成那行
> 没有的片段、引一个不存在的模块、重复引同一条）**五处都红**。下半：把那个写法

#### 裁决：三种结果不是两种，而且**判不了的不算没通过**

```bash
python -m verification.adjudicate     # 读 verification_report.json，写 ADJUDICATION.md
python -m verification.selfproof      # 拿单点扰动去试上面那张表，写 SELFPROOF.md
```

三条复现各自报「达到预期／没达到预期／没测到」，那是**每一条自己的**判定。
`adjudicate.py` 做的是另一件事：把三条复现的**读数**摆到一张桌上，用一套**跨复现的**
判据再判一遍 —— 像「守卫关与守卫开的记录数至少差两个数量级」这种话，任何单独一条
复现都判不了。

它判成**三种**，不是两种：

| 结果 | 含义 | 采信 |
|---|---|---|
| **通过** | 判据成立 | 另有一列 `trusted`，见下 |
| **否决** | 判据不成立 | 同上 |
| **不可判定** | **缺读数**，判不了 | 恒为「不谈」 |

**「判不了」既不算通过也不算否决。** 所以这张表**没有分母**，也不产生任何比率 ——
**「多少条里多少条通过」不是这里的读法**（照当下的表说就是「15 条里 13 条通过」，
但这两个数会随判据表变、**别抄**）—— 那 2 条判不了的是**根本没被判定**，不是「没通过」。
产物开头就把这句话写在最前面，它是判据表**自己**交代的：缺了这句，检查器直接抛、
不生成表（一句话不能由检查器代说，代说就成了贴标签）。

四件事值得单说：

* **采信（`trusted`）与结果分开，而且是一串理由不是布尔。** 两条规则：
  **贴界一票降级** —— 判据读到的格子里有一个是**贴界**的（值被机制压住、失去分辨力），
  这条就不采信，量还在，但它分不出差别；**判据恒真** —— 见下。判不了的判据
  `trusted` 记 `None`：记 `False` 会让「不采信」这个数虚高，记 `True` 又等于说它可信。
* **贴界按单元格判，不按「臂的集合 × 量的集合」的乘积判。** 乘积式的判法会让
  「一格贴界」变成「整行整列降级」，判据于是比它该有的强得多，而且强得没人看得出来。
  这一处有变异 `J1` 盯着：把判法退化回乘积，测试当场红。
* **每条判据自带一个 `falsifier`：一处具名的单点读数改动，能把这条判据弄红。**
  给不出、或者给了却翻不动它的 → 检查器**自己**判它**恒真**、记 `trusted=False`，
  理由写明「任何单点扰动都翻不动它」。于是「这套判据有没有鉴别力」是**机检**的，
  不是声称的。`selfproof.py` 就是那台自证的机器：15 例单点扰动，每例配一张表态表
  （`touch` 会变的那几条 + `untouched` **不许变的那几条**，两者必须恰好覆盖全部判据，
  漏一条就报错），三个扰动层（读数／断言／边界）各有例子。
* **五格必须全出现过**：通过·采信／通过·不采信／否决·采信／否决·不采信／不可判定。
  少一格就是有**死格** —— 那套判据压根到不了那个状态，到不了的状态上写着的规则都是空话。

> **这张表不证明装置是对的。** 它证明的是「这套判据对这批读数有鉴别力」。
> 判据是我们写的、读数是我们量的 —— 扰动能证明「一处改动会让它动」，证明不了
> 「两边不会一起错」。真锚在**对照臂**上：最有分量的那批判据不是「270 好不好」，
> 而是「守卫关与守卫开**必须不同、且朝这个方向不同**」。
>
> 还有一条：这套判据上线时抓出的第一条是**装置自己**的。`repro_03` 打着一行
> 「两次真实 LLM 调用之间的耗时差是毫秒到秒量级」的 `√`，而它**背后没有任何读数**
> —— 脚本自己在下一行承认这是「外部前提……量不到它」。裁决表里它是一条
> **不可判定**，`to_make_decidable` 写着「量一次真实 LLM 调用的往返耗时差」。
> 这正是本文件下面「退出码：三种不是两种」那一节说的事，而它发生在**我们自己的
> 房子里**。先让检查器抓住它，比替它辩解有用。

**这两个命令自己也走三态退出码**，理由和三条复现一样（都是「没测到 ≠ 没达到预期」）：

| 码 | 含义 |
|---|---|
| `0` | 表生成了，且没有判据恒真 |
| `1` | 表生成了，但**有判据恒真** —— 那张表里有一格是白写的，是发现，得看一眼 |
| `2` | **前提不成立**（报告不在、判据表缺声明）—— 不甩 traceback，只说你该先跑哪条命令 |

> ⚠️ 这一档也是踩出来的：原先 `adjudicate` **不管判出什么都退 `0`**，
> 恒真判据只打在屏幕上；报告不在呢，它甩一个 `KeyError` 式的 traceback 退 `1`
> —— 也就是**把「没测到」报成了「没达到预期」**，正是这张表专门用来抓别人的那件事。
> `J4` / `J5` 两处变异现在钉着这两条：让恒真也退 `0`、让「没测到」退 `1`，各自当场红。

**「产物没过期」查的是结果表，不是文件。** 产物里记着它判的是哪一批读数
（`generated_at` + 读数指纹），但**判过期不拿这两个比**：

```bash
cd backend && python -m verification.run_all     # 任何一次重跑都会重写报告
python -m pytest verification/tests -q           # 这一条仍该是绿的
```

读数里有**物理时钟取样**（`clock.tick_ns` / `gap_s` / `ticks_ratio`），
**每次运行本来就不一样** —— 拿它当过期判据，等于「谁重跑一遍谁就红」。
所以查法是照这份产物**自己声称的**来：把盘上那份报告**重新判一遍**，比结果表。
读数变了但没动摇任何一条判定 → 这张表没过期；哪条判定的结果变了 → 真的过期，
或者那条判据本来就在抖动的量上（那也是要看一眼的发现）。
报告不在（刚 clone 下来还没跑过 `run_all`）→ **跳过，不是失败**：
这不是产物有问题，是这一条**没条件判**。

> ⚠️ 这一条**踩了两次**才踩对，两次都是**假警报**：第一版钉报告文件的
> **sha**（报告每跑一次就重写，`generated_at` 必然不同）；改成钉**读数指纹**之后
> **照样每次重跑都红**，因为指纹里含着物理时钟取样。两个版本的共同毛病是
> 「钉了一个**每次运行都不该相同**的东西，然后说它不同就是有问题」。
> 这是**每一个照 README 跑一遍的人**（clone → `run_all` → `pytest`）都会撞上的，
> 所以它不是在报告一个小毛病，是在制造一个不存在的毛病 —— 与
> `MUTATIONS.md` 里那处「跳过挂太宽 → 假绿灯」是同一类错的另一面。

> ⚠️ **同一件事还有第三次，错在对面**（2026-09-20 实测抓到）：这次不是「假红」，
> 是**该跳的没跳**。核 README 那三个数的测试要读三份本机产物，而产物不入库 ——
> 刚 clone 下来它一度**抛 `FileNotFoundError` 的 traceback 红掉**，而上面那句
> 「第一次跑是 `243 passed, 2 skipped`」写的是干干净净的跳过。
> **判不过和没条件判是两回事**，那一处正好把前者安在了后者身上。
> 现在它和隔壁那条一样先问前提（缺产物就报「没条件判」），
> 并且配了一条**不依赖本机产物**的反向对照（把产物读数换成一组明显不对的数，
> 比对照必须当场响）—— 免得「都跳过去」也变成一种绿。
> 上面那句（当时是 `243 passed, 2 skipped`）就是拿真 clone 重测出来的 ——
> 那个数后来随条数涨成了 `251 passed, 3 skipped`，**它当时的来路不变**。

## 端到端：替身模型跑一整局

```bash
python -m verification.e2e_stub            # 三档臂，约一分二十秒（本机一次实测 24.8 / 31.8 / 20.8 秒，
                                           # 合计 77.4 秒；几次运行落在 74 ~ 82 秒）
python -m verification.e2e_stub --keep     # 留下临时目录，方便逐字看现场
```

**这条命令补的是上面那个「跑了也看不见」的洞。** 它把上游那个驱动脚本**原样**拉起来
（子进程，不是把管线重搭一遍）：

```bash
python scripts/run_parallel_simulation.py \
    --config <临时目录>/simulation_config.json \
    --reddit-only --max-rounds 1 --no-wait --guards both
```

`SocialAgent`、`AgentGraph`、`OASIS env.step()`、camel 的工具调用环、记忆写入路径、
平台 SQLite —— **全是真的**。被换掉的只有一样：**模型的决策**
（`stub_model.ToolStubModel` 顶掉 `ModelFactory.create`）。**不发一个字节的网，
不需要 key。**

### 三档臂：同一份代码 + 一个受控旋钮

**没有「守卫关」这条臂。** `--guards off` 时守卫根本没装，`counters()` 恒为全 0 ——
读不出东西来。所以三档**全部** `--guards both`，彼此只差一个旋钮：

| 臂 | 旋钮 | 想走到守卫的哪一支 | `written_whole` | `still_sliced` | `timestamp_pushed` | 库里帖子 |
|---|---|---|---|---|---|---|
| `roomy_e2e` | 一次响应一个动作、消息放得下 | 快路径写入 | 8 | 0 | **1 ~ 2** | 2 |
| `bigtext_e2e` | 助手消息文本 20000 字 | 「自己就超上限」的回落支 | 6 | **2** | 0（贴界） | 2 |
| `two_e2e` | 一次响应两个 `create_post` | 同拍写入（时间戳被推） | 12 | 0 | **1 ~ 2** | **4** |

> ⚠️ **`timestamp_pushed` 那一列是观测量，不是刻度 —— 左边三列才是可复现的。**
> 判据在 `camel_guards._next_timestamp`：拿 `time.time_ns()` 取一个时刻，看它有没有落在
> 上一条之后的一个 `STEP`（`1e-3` 秒）之内。**机器忙的时候写入本来就慢，撞上的次数就少。**
> 同一台机器、同一份代码实测到过 **1 和 2**（两档臂各见过两种值），所以这里写**区间**。
> 左边三列（条数）由消息内容决定，跟快慢无关 —— 实测改过一轮夹具花名册之后它们**一个字没动**。
> 这个区别正好是本装置在别处反复讲的那一条：**别去钉一个本来就会合法地变的东西。**

### **这一格能诚实主张什么**

**能主张：守卫的两个分支都被真实流量走到了** —— 快路径写入走通、超限回落支走通、
同拍写入被推时间戳、动作真的落进平台库。

**不能主张：它不证明「守卫修好了什么」。** 那是三条离线复现的活：它们量的是
「装上前后差多少」，本命令量的是「**装上了、并且被走到了**」。它也**不证明仿真质量**
—— 模型是替身，关于「真 LLM 下行为如何」一个字都不主张。**这条界线写进了产物**
（`e2e_report.json` 的 `what_it_does_NOT_prove`），不只是写在这里。

### 三处踩出来的东西（都改过一轮，不是猜的）

* **`max_tokens` 不能当旋钮用。** 它同时是 `ScoreBasedContextCreator` 的上限：
  收得太紧，`get_context()` 抛 `RuntimeError`，`chat_agent.py:2004-2007` 接住之后
  **直接把这一轮终止** —— agent 在能写任何东西之前就没了动作，**看起来像跑通了**。
  实测 `max_tokens=150` → 0 个动作、库里 0 帖。
* **平台用 Reddit，不用 Twitter。** Twitter 的推荐系统硬依赖 HuggingFace 的
  `Twitter/twhin-bert-base` 权重；离线时那个异常被 `platform.py` 吞掉，
  推荐表**永远静默不更新**。Reddit 的 `rec_sys_reddit` 不需要任何模型。
* **替身必须无状态。** `env.step` 并发跑所有 agent，而 `chat_agent.py:468-471`
  给每个 agent 各包一个 `ModelManager`、包的却是**同一个后端实例**。动作由
  「旋钮 + 消息内容」决定，不由可变游标决定 —— 这条有测试钉着。

> 顺带记一笔**上游**的：`oasis/social_agent/agents_generator.py:574` 的
> `open(profile_path, "r")` **不指定编码** —— 中文 Windows 上默认 GBK，读 UTF-8
> 花名册当场 `UnicodeDecodeError`。**任何中文 Windows 用户走 Reddit 路径都会撞上。**
> 本命令的绕法是花名册用 `ensure_ascii` 写。

### 读数怎么落盘

`camel_guards.install()` 在**装了守卫的那一侧**注册一个 `atexit`，把 `counters()`
写到 `$GUARD_COUNTERS_OUT`。**文件不在 → 报「没测到」，不编数**（同 `_reconcile`
的纪律）。落盘写在守卫里而不是驱动脚本里，所以**上游三个脚本仍然一行都不用改**。

**退出码**和装置其余部分同一套：`0` 三档都量到 · `1` 某一档子进程失败 ·
`2` **没测到**（超时、产物缺失）—— 都不折进「通过」或「否决」。

**转录是抹过的，不是逐字。** 这一份和 `run_all` 的报告**故意的不同**：日志里必然
带着**本机的临时目录和用户名**，而这份产物**是要提交进仓库的** —— 逐字抄一遍就是
把造它那台机器的路径钉进公开仓库。抹掉的是：运行目录、`backend/`、系统临时根、
主目录、行首的 `[HH:MM:SS]` 时间戳。替换清单写在产物里（`redaction_applied`），
**不藏着**。

### 缺了这一份会怎样

`e2e_report.json` 是**入库**的（不像 `verification_report.json` 那样被 gitignore）。
把它挪走，裁决器不会静默少几条：端到端那五条判据**变成「不可判定」**，
`to_make_decidable` 写着该跑哪条命令 —— 用上三态里那一格。
`selfproof` 更硬一点：它那 15 例的表态是照着「这一层有定论」写的，
**缺了它就退 2（没测到），不假红**。

## 退出码：**三种，不是两种**

| 码 | 含义 |
|---|---|
| `0` | 三条都达到预期，且对账一致 |
| `1` | 有任意一条**没达到预期**，或**两份材料对不上** —— 这是真的要看的东西 |
| `2` | 有任意一条**没测到**（缺依赖、源码对不上……），或对账有一边抽不出数 |

`2` 和 `1` 分开是刻意的：**「没测到」不等于「通过」，也不等于「失败」。**
一个装置如果把「没跑起来」报成绿色，它后面所有的绿色都不值钱了。

> ⚠️ **这一节有过一次真的翻车，记在这里。** 三种退出码写在文档里，代码却只发得出
> 两种：三条复现原先一律以 `sys.exit(0 if main() else 1)` 收尾，而 `main()` 的签名是
> `-> bool | None`，三份文件里大量 `return None` 正是「没测到／前提不成立」的写法。
> `None` 是假值 → **退出码 1**。于是 `2` 这一档对三条复现是**死档**，而下面的
> 结论那一节还明写着「核对不上会报『没测到』并给退出码 `2`」—— **那句话是假的**。
>
> 发现它的方式是把 `repro_03` 的引文行号挪开一行，制造一次真的「没测到」，
> 看退出码；拿到的是 `1`。修法是三条复现统一走 `_probe.exit_with(main())`
> （`True→0` / `False→1` / `None→2`，按 `is True` / `is False` 分），
> 正常路径的退出码不变（仍是 `0`），读数与打屏文本一个字没动。
>
> 记这一笔是因为它比「多一条亮点」更像一个真在维护的装置：**这一节要求的纪律，
> 装置自己先是违反的。** 同一件事的第二个例子见上面「裁决」那一节 ——
> 检查器上线抓到的第一条，就是本装置自己打的一个没有读数支撑的 `√`。

## 最后那步「对账」：装置和**准备发出去的材料**有没有走岔

`run_all` 跑完三条复现之后，还会再对一次账：`upstream/` 里那两份**最小复现**
（它们是**准备贴进上游 issue 的原文**）报的数字，和装置本体报的，是不是同一组。

```
                装置      草稿      对账
  ------------  --------  --------  ---------
  ① 新增记录数  270       270       √ 一致
  ① 实增 token  5130      5130      √ 一致
  ② 同拍违反数  1         1         √ 一致
```

**为什么这值得单独一步：那份「一致」本来是个巧合。** 两边**输入根本不一样** ——
装置那条探针消息是「【记录开始】…数据 数据…【记录结束】」（763 字），草稿那条是
「记录0，记录1，…记录89，」（440 字）。两条完全不同的消息，在这个分词器下
**都恰好数出 277 token**，于是记录数与实增 token 撞在了一起。换分词器、或者谁改了
一边的探针消息，两边就会各走各的 —— **那正是这一步要响的地方**：它比的就是这三个数，
任何一边动了而没重跑它，它当场报 `×` 并退 `1`。

这一步**不重跑**装置那三条（它们的正文刚跑出来还热着），只跑那两份草稿，
多花十来秒。它**不并进汇总里那个 `x/3`** —— 三条复现回答的是「仿真会不会坏」，
对账回答的是「我们的材料有没有走岔」，两件事不该混成一个比率。报告里它另起一节，
`.json` 里在 `reconciliation` 键下，并显式标了 `not_a_fourth_reproduction: true`。

> 也**验过它会红**：把草稿①的探针消息从 90 条记录改成 88 条，对账立刻报
> **不一致**（270 → 264、5130 → 5016 两行都标 `×`）并给出退出码 `1`，
> 而三条复现自己**照样是绿的** —— 这正是它要抓的那种错：复现没坏，
> 是准备发出去的那份材料走岔了。产物在 `RECONCILE_SELFCHECK.md`（见下）。

#### 对账留痕：上面那句「验过它会红」，产物在 `RECONCILE_SELFCHECK.md`

和 `MUTATIONS.md` 同一个形状 —— **改坏 → 跑 → 记录 → 逐字节还原**，两轮：

```bash
python -m verification.reconcile_selfcheck     # 在 backend/ 下跑；约五十秒（本机实测 48.9 秒）
```

| 轮 | 改了什么 | 跑什么 | 期望 |
|---|---|---|---|
| **A** | 什么都不改 | 装置①、装置②、草稿①、草稿② | 对账退出码 **`0`**，三行都「一致」 |
| **B** | 草稿①的探针消息 **90 条 → 88 条** | 只重跑草稿① | 退出码 **`1`**，①的两行「不一致」、②那行仍「一致」 |

三件值得单说的事：

* **它不重跑装置那两条，而且这不是偷懒。** 植入只动了草稿那一个文件，而三条复现
  **都不读草稿** —— 脚本当场静态核一遍这件事（`repro_0*.py` 里不出现 `upstream`），
  所以装置侧的正文在两轮之间是**同一份文本**：不是「重跑后仍然一致」，是**根本不受影响**。
  把这句话说清楚，比多花几十秒再跑一遍更有用，而且它不会因环境而变。
* **它证明的和不证明的**：对账只回答「两边是不是同一组」，**回答不了「这一组数对不对」**。
  后者是复现自己那条线的事。产物里显式标了 `not_a_pass_rate: true` ——
  **B 轮那个退出码 `1` 是期望的结果**，不是失败率。
* **报告不许过期**：`test_reconcile_evidence.py` 拿脚本哈希、两份草稿的哈希，外加一条
  「植入点 `range(90)` 是不是恰好还剩一处」去核对报告 —— 草稿改了而没重跑留痕，
  普通 `pytest` 会先红，并且告诉你敲哪条命令。

## 三条各自在说什么

### ① 切片正反馈环 —— `repro_01_slicing.py`

`camel/agents/chat_agent.py` 的 `update_memory`（中间的空行与注释行略去，其余**逐字**）：

```python
# 逐字引自 camel.agents.chat_agent
remaining_budget = max(0, token_limit - ctx_tokens)            # 884
if current_tokens <= remaining_budget:                         # 886
    _write_single_record(message, role, base_ts)               # 887
    return                                                     # 888
base_chunk_size = max(1, remaining_budget) // 10               # 933
sample_prefix = "[chunk 1/1000 of a long message]\n"           # 942
prefix_token_len = len(token_counter.encode(sample_prefix))    # 943
chunk_body_limit = max(1, base_chunk_size - prefix_token_len)  # 948
num_chunks = math.ceil(len(all_token_ids) / chunk_body_limit)  # 951
```

> 那个第一行 `# 逐字引自 …` **不是**装饰：`tests/test_citations.py` 认这个标记，
> 之后每一行末尾的 `# 数字` 都会**逐字**拿去和上游第 N 行比。写这一段的时候
> 它当场红过一次 —— 原先这里把 942 行的那个字面量**拼进了 943 行的表达式**，
> 于是摆在读者面前的是一行**上游根本没有**的代码，而它看着比真的还顺眼。

上面几行的意思：
`remaining_budget` 用的是**截断后**的 `ctx_tokens`（884）；`if` 不满足才走切片（886）；
残余预算先被 `// 10` 砍一刀（933）；正文容量要再减去**前缀**（942 / 943 / 948）；
条数由正文容量算出来（951）。

（`prefix_token_len` 在 `gpt-4o-mini` 的编码下量出来是 **12**，但上游写的是这个
表达式、不是字面量 —— 换个分词器就不是 12 了。）

截断干的事就是把上下文填到贴着上限，所以 `remaining_budget` **按构造就远小于
待写的消息**；它还要再被 `//10` 和减前缀这两刀砍。

**这个窗口比「预算很紧」宽得多。** 把 12 代进去算一下：只要
`remaining_budget < 140`，`chunk_body_limit` 就落到 1 —— 也就是**只要残余预算
不到 140 token，每一条被切的消息都变成一块一个 token**，每块还各带一个十几
token 的前缀。上限 4000 的上下文里这几乎是常态。

实测（上限 4000）：一条 **277 token** 的消息 → **270 条记录、实增 5130 token
（18.5 倍）**，原文被撕得找不回连续的「记录开始」。而这是个正反馈环：
记忆满 → 残余预算小 → 切片 → 膨胀 → 记忆更满。

装上守卫后：**1 条记录、实增 277 token、原文完整**。

判据是机检的，不看叙述：**这条消息自己 ≤ 上限，却仍然被切了** → 不是必要的切分。
「预算只是紧」本该交给 `ScoreBasedContextCreator` 去驱逐旧记录，camel 把两种
情形合并进了同一个条件。

### ② 同拍碰撞 —— `repro_02_timestamp.py`

`_record_tool_calling`（方法在 **2691** 行起，下面贴的这段读钟在 **2739~2751**）
**只读一次时钟**，用 `+1e-6` 把回执排在
请求之后，注释写着「纳秒精度，避免碰撞」。而**那个 `1e-6` 细到两种机器上都靠不住**：
Windows 上它比时钟自己的分辨率细两三个数量级（脚本第一节现场量出最小步长零点几
毫秒 —— 40 次取样 0.30 ~ 1.00 ms）；换到 Linux 上时钟刻度比它还细（实测 **100 ns**），
于是它**反过来比一拍粗十倍**。**两个方向上它都分不开两次挨得太近的调用。**

所以它分得开**一对**请求/回执（那是加在显式值上的算术，不看钟），却分不开
**两次调用**：一次模型响应里并排的两个 tool 调用前后脚读钟，**落点相差只要小于
那个偏移**，四条记录就照样交错 —— 「读到同一个 `T`」只是这个条件在真实机器上
最常见的取值，不是它的全部。

**分界是那个偏移，不是时钟刻度。** 第二节的四臂就是照这件事构造的：间隔取
`0 / 半个偏移 / 两倍偏移 / 0`（守卫开）—— 换算成纳秒是 `0 / 500 / 2000`，
**不是按本机量到的一拍定的**，所以在哪个平台跑都是同一件事，判定也一样。
（这一条是 2026-09-19 换平台跑出来的：原先那一臂的间隔取的是「当场量到的一拍」，
在 Windows 上恰好等价于「跨过了那个偏移」，看着像「跨拍就免疫」；Linux 上同一臂
照样违反。改法是把输入写成与宿主机无关的量。）
四条记录的时间戳成了 `T、T+1e-6、T、T+1e-6`，而排序键 `(timestamp, -score)`
在相等处按**分数高的在前**决胜负 —— 也就是**后写的那条排到前面**：

```
assistant_B(T) · assistant_A(T) · func_B(T+1e-6) · func_A(T+1e-6)
   ↑ 带 tool_calls     ↑ 紧随其后的却是另一个 assistant，不是它的回执
```

端点回 400 `insufficient tool messages following tool_calls message`，而上层只记
一行 `Agent ... error` 就继续跑 —— **该 agent 这一轮的动作整条消失**。

判据直接对**发给 API 的那串消息**做 API 的同一条校验（`memory.get_context()`
返回的就是它）：凡带 `tool_calls` 的消息，紧随其后的必须是回应它的 `role="tool"`。

> ⚠️ **这一节里的时间数字全是量出来的，写在这里的区间是观测范围，不是常数。**
> 本机 40 次取样：一拍 **0.30 ~ 1.00 ms**（中位数 0.37）—— 随系统调度变，最小步长
> 本身就是个随机量。脚本**每次运行都重新量一遍**，报告里是那一次的数，和这里写的
> 不会逐位相同，**这是设计如此，不是对不上**。
>
> 与之相对：**第二节那张表**用的是冻钟，每次运行逐位相同 —— 只有它是可逐位复核的，
> 而**判据只用它**。第三节的两个数不进判据（物理时钟量出来的东西不该有否决权）。
>
> **第三节那两行的稳定度差得远，别当成一回事：**
>
> - **切片没修**：7 次运行 106.8 ~ 122.7 ms，折合上百到三百多拍 —— 稳，因为它由
>   「要落几百条记录」这件实际工作决定，跟时钟分辨率无关。
> - **切片修了**：7 次运行 **0.00 ~ 3.80 ms** —— 5 次直接同拍，**2 次跨到十来拍**。
>   也就是说**这一行会抖出「同拍」**。所以第三节量的是**趋势**（间隔被拉进了拍的
>   量级），不是「修了①就一定同拍」这条保证。
>
> 「同拍就一定拆散」那条由第二节的冻钟定死；第三节只负责说明这个范围**碰得上**。
>
> 顺带：表里「合多少拍」的分母是**本节当场另量**的一拍，与第一节那个数不是同一次
> 测量，本来就不相同 —— 所以这一列比左边「间隔」那一列更不稳，读的时候分开看。

**这条失效是①的代价，脚本第三节把它量了出来：**

| | 两次 tool 调用的真实间隔 | 后果 |
|---|---|---|
| 切片没修 | **一百多毫秒**（7 次运行 106.8 ~ 122.7 ms，折合**上百拍**） | 跨拍 → 误打误撞免疫 |
| 切片修了 | **拍的量级**（7 次运行 0.00 ~ 3.80 ms；5 次同拍，2 次跨到十来拍） | 同拍才碰撞 |

切片没修时写一次回执要落几百条记录、花上百毫秒，两次调用必然跨出很远；切片的修复
**全部目的就是让写入变快** —— 把它拉回拍的量级，碰撞才开始碰得上。

### ③ 并发次序 —— `repro_03_concurrency.py`（**边界，不修**）

这一条和上面两条同等重要，它不是「没做的东西」，是**划出来的边界**。

上游 issue #751 / #759：同一份输入跑两次跑出不同人群（弃权率 9.5% vs 60.0%），
温度设 0 也一样。成因在 `oasis/environment/env.py`：

```python
# 逐字引自 oasis.environment.env
semaphore: int = 128,                                  # 55
self.llm_semaphore = asyncio.Semaphore(semaphore)      # 70
async with self.llm_semaphore:                         # 127
await asyncio.gather(*tasks)                           # 193
```

（脚本第一节会**在真实源码里逐行核对**这几行；对不上就报「没测到」，不报「通过」。
引文里原先写在行尾的两处说明搬到这里：**127 行**是 `_perform_llm_action` 里那句
`async with`，**193 行**把一轮里所有 agent 的动作一起发出去。
MiroFish 的驱动脚本把并发数设成 **30**，也是从脚本里读出来的，不是记的。）

**谁的 LLM 先返回，谁的动作就先落库** —— 落库次序决定 `post_id` 的分配，进而决定
后续交互指向哪条帖子。而次序取决于网络快慢，那是程序管不到的量。

脚本量出两件事：

* **次序是「耗时」的确定函数**：耗时全相同时跑两遍，次序逐位相同。
  **乱的不是事件循环，是喂给它的耗时。**
* **灵敏度极低**：把 0 号 agent 拖慢 **0.1 毫秒**，落库次序就变了。
  而两次真实 LLM 调用的耗时差是毫秒到秒量级 —— **根本没有安全余量。**
  这是**判据用的那一格**（栅格上两个平台都翻的那一格）。栅格上更小的格点本机也翻
  —— Windows **1 微秒**、Linux **100 微秒** —— 但那个「最小的那一格」是**宿主机
  调度粒度**的性质，换台机器就变，所以它只作读数、不进判据。**这一条也是
  2026-09-19 换平台跑出来的**：原先判据取的就是本机那个 1 微秒。

**为什么不能靠「排个序」修掉**：要让这一层逐字可复现，就得把 agent 的动作串行化；
而并发正是这个仿真跑得动的前提。**换来的确定性和花掉的时间，是取舍，不是对错。**

所以装置的立场是：**这一层不承诺可复现，只承诺可检出。**

## 这套东西在「可复现性分层」里的位置

「可复现」不是一个布尔值。同一个仿真里，有的层天然确定，有的层原理上做不到 ——
把它们混成一句「我们可复现」，是这类项目最常见的一句空话。这一节说的是这套
装置**管到哪一层，以及哪一层它不管**。

| 层 | 要回答的问题 | 这套装置 |
|---|---|---|
| **引擎** | 同样的输入，引擎的行为是不是逐位相同 | **管**，而且这是两个守卫的全部目的 —— `repro_01` / `repro_02` 量的就是它 |
| **产物** | 同一份引擎产出，是不是渲染成同一份文字 | **管**，方式是**逐字转录**：报告里那段正文就是当时屏幕上那段 |
| **端到端** | 同一条命令，是不是跑出同一个社会 | **不管**，`repro_03` 只说明它由什么决定、为什么钉不住 |

> ⚠️ **「能跑到那一层」不等于「管住了那一层」，这两句别混。** 替身模型那一跑
> （见上）确实**跑进了第三层**：一整局仿真、真环境、真写入。但它主张的是
> 「守卫的分支被走到了」，**不是**「第三层可复现」—— 恰恰相反，第三层为什么
> 钉不住，仍旧只有 `repro_03` 那一条在说。**跑得到，是证据的覆盖面变宽；
> 管得住，是要输出的确定性。这一格两样都没有换来。**

前两层之所以管得住，是因为它们里面**没有 LLM**：守卫改的是记忆写入，
转录读的是已经打出来的字节。第三层管不住，是因为它每一步都在问模型 ——
温度设 0、固定 seed 也只能收窄抖动，服务端给不了逐位保证。

**把管不住的那一层如实报出来，比含糊掉它重要得多。** 这也是为什么第 3 条复现
和另外两条一样进退出码、一样写进报告 —— 它不是「没做的东西」，是**划出来的边界**。

从这套分层回头看，两个守卫的分工也就清楚了：它们不是「让仿真更准」，
而是**把引擎那一层从「不确定」挪到「确定」**，并且把这次挪动**是拿什么换的**
（见上面那张 ①→② 的代价表）说明白。

## 三个守卫是什么关系

```
camel_guards.install(target=None, slicing=True, timestamp=True)
camel_guards.set_flags(slicing=..., timestamp=...)   # 只改开关，不重装
camel_guards.uninstall()
camel_guards.counters()
```

替换的是 `ChatAgent.update_memory` **一个方法，一处补丁**，两个开关在这里读。
`target` 是给测试用的注入口：传一个替身类就能在不碰 camel、不发 LLM 的前提下把
「该拦的拦、该切的不切」两个方向都测到。被替换的原方法留在内部、
`uninstall()` 可完整还原，`install()` **幂等**。

计数（`counters()`）落进调用方的产物：

| 名字 | 含义 |
|---|---|
| `written_whole` | 整条写入的次数 |
| `still_sliced` | 消息**自己**就超上限、必须切才交回原方法的次数 |
| `timestamp_pushed` | 我们自己取读数、却被推后的次数 |

⚠️ **`timestamp_pushed` 不是「撞窗口的次数」，别那样读它。** camel 显式给的
请求/回执那一对**几乎总会被推**（它的 `1e-6` 小于一个步长），那是把次序撑开、
不是撞上。这个计数只回答「有多少次读数是靠逻辑时钟补救的」。

## 已知边界

* **两个平台上都跑过了 —— 而且第一个平台之外的这一次，把装置改掉了。**
  本机是 Windows 11 + CPython 3.11.9；2026-09-19 又在一台 Linux（Ubuntu/WSL2 +
  CPython 3.11.16，时钟刻度 **100 ns** vs 本机 **375500 ns**）上从干净 clone 跑了一整遍。
  结果是**三条判据里两条当场翻成「否决」**，外加一处渲染器崩溃 —— 都修了，
  改法是同一个：**判据的输入写成与宿主机无关的量**（复现②的间隔按 camel 那个偏移
  定义、复现③取两平台都翻的栅格点），本机量到的数降级成读数。
  两条机器检查（`tests/test_repro_verdicts.py`）现在钉住这件事，防止判据被写回
  宿主机上量出来的数。**这一段是「自证」的一部分：装置把自己拿到第二个平台上跑，
  量出两处判定会翻，改完重跑 —— 而不是在报告里写一句「换平台应该也一样」。**

  * **会变的：环境读数。** 物理时钟的步长（复现②那一节量过的那个数）、复现③栅格上
    「最小的那一格」、真跑那一局里线程的实际交错次序 —— 这几样是**这台机器**的性质，
    换平台会差几个数量级（本机 375500 ns，Linux 100 ns；「多小的耗时差就能让次序变样」
    本机 1 微秒、Linux 100 微秒）。它们只作**读数**，**不进判据**。
  * **不会变的：判定。** 修好之后在 Linux 上重跑，三份产物的判定与本机一致
    （`run_all` 3/3、`adjudicate` 13 通过 / 0 否决 / 2 不可判定、`selfproof` 15/15）。
    被裁决的**实验臂**用的是**冻钟**与纯逻辑，不读物理时钟（受判的臂显式声明
    `frozen_clock: True`，现场量到的时钟读数在表里标成「前提读数，不是实验臂」）。
    **这句话现在是量过的，不是构造上推的** —— 推的那一版已经错过一次了。
  * **一个要读准的地方**：上游 issue 草稿里「那个 `1e-6` 比时钟自己的分辨率还细两三个
    数量级」这句，是**对着 Windows 的时钟步长**说的。这个比较在 Linux 上真的**翻转**了
    （那边 1 微秒比一拍还粗十倍）—— 所以草稿把那台机器量出来的步长**写在旁边**，
    读的人可以自己换算。**草稿论证的是「碰撞窗口比时钟刻度细」，这件事本身与平台无关；
    有平台色彩的是用来举例的那两个数量级。**
* **装置只对 MiroFish 类 · camel-oasis 系仿真实例有效**，**不承诺支持任意框架**。
  这是边界，不是缺陷：两个守卫改的是 `camel.agents.chat_agent.ChatAgent` 的
  运行时行为，判据也建立在这条调用链上。
* **第 3 层（端到端）：能跑到了，但仍不承诺可复现。** `python -m verification.e2e_stub`
  用替身模型把一整局真跑完（真环境、真写入，只换掉模型的决策），补上了
  「守卫的两个分支被真实流量走到」这一格；**但它不管「同一条命令是不是跑出同一个
  社会」** —— 那是 `repro_03` 划的那条界（见上）。注意两者**结论方向相反、互不抵消**：
  一个说「跑到了」，一个说「钉不住」。**「跑到」不是「管住」。**
* **`repro_03` 不证明 MiroFish 端到端不可复现**，装置里也没有任何一条**证明**它可复现。
  真要主张「跑两次一样」得真跑**真 LLM** 的两次 —— 而那不只是缺个 key：
  「跑两次不一样」本身也不构成证明。它只说明这一层的次序由什么决定、为什么钉不住。
* **替身那一跑的读数不构成「守卫有效」的证据。** 它量的是**走到了哪一支**，
  不是**装上前后差多少** —— 后者是 `repro_01` / `repro_02` 量的。三档臂全装同一套
  守卫，所以它内部**没有对照臂**，这一点是刻意的、也是它的上限：`bigtext_e2e` 的
  `timestamp_pushed` 那一格**按构造恒为 0**，在表里如实记成**贴界**、裁决时**不采信**。
* 上游 web 半边**硬依赖 Zep Cloud**（`zep-cloud`、`ZEP_API_KEY`），没有 key 跑不起来。
  三个缺陷全在 OASIS/camel 路径上，而 `scripts/run_*_simulation.py` 不 import `app/`，
  所以本目录**完全不需要 Zep**。
