## 为什么提给 MiroFish，而不是 camel-ai / camel-oasis

两个缺陷的**根因代码都在 `camel-ai` 里**（`camel/agents/chat_agent.py` 的
`update_memory` 与 `_record_tool_calling`）。但报告提到 MiroFish，理由是：

* 出问题的是 **MiroFish 的行为** —— 用户跑 MiroFish 时看到的是「某个 agent 这一轮
  突然没了动作」「账单比预期高一个数量级」，不是「camel 的某个函数返回值不对」；
* 修法落在 **MiroFish 自己的代码里**（驱动脚本包一层守卫），不改 `site-packages`；
* 我们**没有向下游依赖提 issue 的立场**：那两个函数的行为在上游没有明确规格，
  我们只能证明「它这样切会毁掉消息」，不能证明「上游认为这是 bug」。

所以这里的定位是：**把现象、最小复现、和一条不改 `site-packages` 的处置一起交上来**，
由 MiroFish 维护者决定是就地包一层、还是向上游反馈。

## 两条最小复现都不用 API key

两份草稿里的复现都是**自包含**的：不发 LLM 请求、不要 `LLM_API_KEY`、不要 Zep、几秒跑完、
结果确定。做法是用 `ChatAgent.__new__` 绕过 `__init__` —— 真造一个 `ChatAgent` 要一个
模型后端，而这两个缺陷都在**写入决策**上，与模型无关。

（② 那一份额外需要冻住 `time.time_ns`，因为「同不同拍」在真实时钟下由调度决定。
这不影响结论：草稿里同时给出了真实时钟一拍的宽度，说明同拍在现实中是常态。）

**一处例外，免得把「自包含」读大了：** 两份复现都要一个真的分词器
（tiktoken 的 `o200k_base`），而它的编码表是**首次使用时下的**一份静态数据
（约 3.6 MB，之后走本地缓存）。缓存热的机器上不发任何请求；冷缓存时要下这一次。
这不是 LLM 调用，但确实用到网 —— 而且它省不掉：① 那份复现的数字
（270 条 / 5130 token）就是它数出来的。

## 这两份草稿和 `../repro_0*.py` 的关系

草稿里的复现是为了**贴进 issue 而另写的紧凑版**；仓库里那三个脚本是装置本体，
多了前提自检、单点扰动、退出码三态、以及「没测到 ≠ 通过」的处理。

**两者的数字必须一致** —— 不一致就是有一边错了。目前对齐情况：

| | 草稿（`repro_min_0*.py`） | 装置（`../repro_0*.py`） |
|---|---|---|
| ① 记录数 / 实增 token | 270 条 / 5130（18.5×） | 同 |
| ② 同拍违反数 / 隔拍违反数 | 1 / 0 | 同 |
| ② 时钟最小步长 | 量出来 0.30 ~ 1.00 ms | 同量级 |

前两行是**逐位必须一致**的，不一致就是有一边错了。第三行是**测量值**，两边本来
就不会相同 —— 它随系统调度变（同一台机器上多次测到 0.30 ~ 1.00 ms，中位数 0.37；
最小步长本身是个随机量，换个时间跑就换个值）。结论只用到
「它比 camel 那个 `1e-6` 大两三个数量级」这一点，两边都满足。

**前两行已经交给机器守了**：`python -m verification.run_all`（在 `backend/` 下）
跑完三条复现之后会多一步**对账**，把两边报的这三个数抽出来逐项比，不一致就
退出码 `1`。**这件事不能靠人记着** —— 两边**输入根本不一样**：装置那条探针消息是
「【记录开始】…数据 数据…【记录结束】」（763 字），草稿那条是「记录0，记录1，…」
（440 字）。两条完全不同的消息，在这个分词器下**都恰好数出 277 token**，于是数字
撞在了一起 —— 这是当下这个分词器的巧合，不是结构保证。换分词器、或者谁改了一边
的探针消息，两边就会各走各的，而不会有任何东西响。

草稿里的两份脚本是**可直接重跑**的：`python -m verification.upstream.repro_min_01_slicing`
（在 `backend/` 下）。① 那份的输出与草稿里的输出块逐字对应；② 那份**冻钟的几行**
逐字对应，**真钟那两行不会**（那一行的步长是测量值，每次跑都不一样，草稿里已经就地
标出来了）。
