> #751 报的是：同一份输入跑两次，跑出不同的人群（弃权率 9.5% vs 60.0%），
> 温度设 0 也一样。下面这段不讲人群构建，讲**模拟层**的落库次序 ——
> 它是同一份输入在不同运行里走向不同结果的另一条通路。
>
> 独立实测，不引用我们自己的项目。

---

## 1. 成因在 `oasis/environment/env.py`，不在模型里

`0.2.5` 的源码里这四行是关键（行号对 `camel-oasis==0.2.5`）：

```python
# 逐字引自 oasis.environment.env
semaphore: int = 128,                                  # 55
self.llm_semaphore = asyncio.Semaphore(semaphore)      # 70
async with self.llm_semaphore:                         # 127
await asyncio.gather(*tasks)                           # 193
```

（127 行是 `_perform_llm_action` 里那句 `async with`；193 行把一轮里所有 agent
的动作一起发出去。）

（顺带：MiroFish 的驱动脚本把这个并发数设成 **30**，不是模块默认的 128 ——
这一条是从驱动脚本里读出来的。）

`asyncio.gather` 把一轮里所有 agent 的动作并发发出去，**谁的 LLM 先返回，谁的
动作就先落库**。而落库次序决定了 `post_id` 的分配，`post_id` 又决定后续的交互
指向哪条帖子 —— 于是一次时序上的抖动会**级联**成两份不同的社会。

## 2. 次序是「耗时」的确定函数 —— 乱的不是事件循环

这一条可能是最重要的：**把每个 agent 的耗时钉死，落库次序就钉死了。**

构造一组**耗时完全相同**的 agent 动作，跑两遍，落库次序**逐位相同**。
但**次序不一定是提交序**：机器几乎空载时它可能就是 `[0..7]`；有负载时会变成
另一串（我们有一次实测是 `[0, 2, 6, 5, 7, 4, 1, 3]`，两遍仍然相同）。

把 0 号拖慢 1 毫秒（抖动远小于 1 毫秒时），0 会被排到最后；**其余 7 个的次序仍随负载变**
—— 几乎空载时是 `[1..7, 0]`，有负载时我们见过 `[1, 2, 6, 5, 3, 7, 4, 0]`。

所以结论是：

> **落库次序是「每个 agent 的耗时」的一个确定函数。不确定的不是事件循环，
> 是喂给它的耗时。**

这也顺带回答了一个常见猜测：**把 temperature 设 0、把 seed 固定，救不了这个。**
因为次序在**模型返回之前**就已经由耗时定了。哪怕模型逐位相同，只要两次运行的
网络耗时差一点，落库次序就不同，`post_id` 就不同，后面所有交互都指向别的帖子。
—— **这不是模型随机性问题，是调度问题。**

## 3. 灵敏度：没有安全余量

阈值**不是常数**：同一台机器两次运行，一次（几乎空载）`1e-6` 是 0/6、`3e-5` 起
每批 6/6；另一次（机器有负载）`1e-6` 就 6/6 翻。贴近阈值的那一档，结果本身
都在抖 —— 几乎空载那一次运行里 `1e-5` 量了两批，一批 5/6（3 种次序）、一批
6/6（2 种次序）。
而两次真实 LLM 调用的耗时差是**毫秒到秒** —— 即使按较大的观测阈值 `3e-5` 算，
也粗 1.5 到 4.5 个数量级；阈值更小的机器上只会更粗。**仍然没有安全余量。**

> **按语（2026-09-19）：这一节给的是量级，不是一个常数。** 阈值随负载变：
> 同一台机器几乎空载时，一批 6 次测量里 `1e-6` 一次没翻、`3e-5` 起每批 6/6；机器有负载时
> `1e-6` 就翻。两次真实 LLM 调用的耗时差是毫秒到秒，即使按较大的观测阈值 `3e-5`
> 算，也粗 1.5 到 4.5 个数量级 —— 「没有安全余量」是这个意思。
> 具体阈值请在你自己的机器上量（脚本会自己报）。

## 4. 为什么不能靠「排个序」修掉

要让这一层逐字可复现，就得把 agent 的动作**串行化**（或者引入一个全局的、
与真实耗时无关的确定性调度）。但并发正是这个仿真跑得动的前提：一轮几百个 agent，
串行化会把墙钟时间乘上并发数。

所以这是**取舍，不是对错**：换来的确定性和花掉的时间，谁更重要取决于用途。
对「要一份可复现的推演」来说是值得的；对「要一个跑得完的大规模仿真」来说不是。

**我们的立场是：这一层不承诺可复现，只承诺可检出** —— 能说清它是被什么决定的、
灵敏度有多高，比含糊地说一句「随机性」有用，也比假装能修好诚实。

## 5. 一个可以立刻落地的中间做法

如果短期内不打算动并发模型，至少可以**把不确定性摊开报**，而不是让它藏在
一份看起来确定的报告里：

* 同一份输入跑 N 次，报**均值与方差**，而不是报一次的数；
* 把每次运行里 `post_id` 的分配次序一并存下来，让两次运行**对得上账**。

这样「跑两次不一样」就从一个 bug 报告变成一条**已知边界**，
使用者也才知道该怎么读那份报告。

---

**复现说明**：上面第 2、3 节的数是离线量出来的，不发 LLM、不要 API key。
把下面这段存成 `concurrency.py` 直接跑。每档跑 6 次，是为了让「时翻时不翻」
这件事自己看得见。

```python
import asyncio

SEM = 30  # 8 < 30：信号量从不阻塞，只为对齐驱动脚本的形状；次序由耗时决定


async def one_round(delays):
    sem, log = asyncio.Semaphore(SEM), []

    async def one(i, d):
        async with sem:
            await asyncio.sleep(d)
            log.append(i)            # 落库次序 = 完成次序

    await asyncio.gather(*[one(i, d) for i, d in enumerate(delays)])
    return log


base = [0.02] * 8
a, b = asyncio.run(one_round(base)), asyncio.run(one_round(base))
print("等耗时两遍：", a, "|", b, "→", "逐位相同" if a == b else "不同")

for delta in (1e-6, 1e-5, 3e-5, 1e-4, 1e-3):
    d = list(base)
    d[0] += delta
    runs = [asyncio.run(one_round(d)) for _ in range(6)]
    print(f"0 号拖慢 {delta:g}s：{sum(r != a for r in runs)}/6 变了，"
          f"{len({tuple(r) for r in runs})} 种次序，如 {runs[0]}")
```

本机（Windows 11 / Python 3.11.9）某次实测——这台机器当时有负载；你的机器上
串和阈值都会不同，脚本会自己报：

```text
等耗时两遍： [0, 2, 6, 5, 7, 4, 1, 3] | [0, 2, 6, 5, 7, 4, 1, 3] → 逐位相同
0 号拖慢 1e-06s：6/6 变了，1 种次序，如 [1, 2, 6, 5, 3, 7, 4, 0]
0 号拖慢 1e-05s：6/6 变了，1 种次序，如 [1, 2, 6, 5, 3, 7, 4, 0]
0 号拖慢 3e-05s：6/6 变了，1 种次序，如 [1, 2, 6, 5, 3, 7, 4, 0]
0 号拖慢 0.0001s：6/6 变了，1 种次序，如 [1, 2, 6, 5, 3, 7, 4, 0]
0 号拖慢 0.001s：6/6 变了，1 种次序，如 [1, 2, 6, 5, 3, 7, 4, 0]
```

同一台机器、另一次（几乎空载）运行是另一组数：等耗时两遍都是 `[0..7]`，
`1e-6` 0/6，`1e-5` 两批分别 5/6（3 种次序）与 6/6（2 种次序），`3e-5` 起每批 6/6
且 0 排最后。两块都是实测；换一台机器、或同一台机器换一次负载，读数还会变。
