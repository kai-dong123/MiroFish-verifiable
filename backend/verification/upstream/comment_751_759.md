# [草稿] 回帖：#751 / #759 —— 我们把成因量出来了，并说明为什么它钉不住

> 这两条 issue 报的是同一件事：**同一份输入跑两次，跑出不同的人群**
> （弃权率 9.5% vs 60.0%），温度设 0 也一样。
>
> **不提新 issue**，在这两条下面回帖。理由是症状我们已经对上，缺的是成因；
> 再开一条只会多一个重复项。下面这段是独立的实测，不引用我们自己的项目。

---

## 1. 成因在 `oasis/environment/env.py`，不在模型里

`0.2.5` 的源码里这四行是关键（行号对 `camel-oasis==0.2.5`）：

```python
 55   semaphore: int = 128
 70   self.llm_semaphore = asyncio.Semaphore(semaphore)
127   async with self.llm_semaphore:            # _perform_llm_action
193   await asyncio.gather(*tasks)              # 所有 agent 的动作并发执行
```

（顺带：MiroFish 的驱动脚本把这个并发数设成 **30**，不是模块默认的 128 ——
这一条是从驱动脚本里读出来的。）

`asyncio.gather` 把一轮里所有 agent 的动作并发发出去，**谁的 LLM 先返回，谁的
动作就先落库**。而落库次序决定了 `post_id` 的分配，`post_id` 又决定后续的交互
指向哪条帖子 —— 于是一次时序上的抖动会**级联**成两份不同的社会。

## 2. 次序是「耗时」的确定函数 —— 乱的不是事件循环

这一条可能是最重要的：**事件循环本身是确定的。**

构造一组**耗时完全相同**的 agent 动作，跑两遍，落库次序**逐位相同**
（实测两遍都是 `[0, 2, 6, 5, 7, 4, 1, 3]`；注意它不是提交次序 `0..7`，
但它是**可重复的**那一个）。

再把其中一个 agent 的耗时**拖慢 1 微秒**，落库次序立刻变成另一串
（实测 `[1, 2, 6, 5, 3, 7, 4, 0]`）。

所以结论是：

> **落库次序是「每个 agent 的耗时」的一个确定函数。不确定的不是事件循环，
> 是喂给它的耗时。**

这也顺带回答了一个常见猜测：**把 temperature 设 0、把 seed 固定，救不了这个。**
因为次序在**模型返回之前**就已经由耗时定了。哪怕模型逐位相同，只要两次运行的
网络耗时差一点，落库次序就不同，`post_id` 就不同，后面所有交互都指向别的帖子。
—— **这不是模型随机性问题，是调度问题。**

## 3. 灵敏度：没有安全余量

1 微秒的扰动就能翻掉次序，而两次真实 LLM 调用的耗时差是**毫秒到秒**量级。
两者差着三到六个数量级 —— **根本没有安全余量可言。**

## 4. 为什么不能靠「排个序」修掉

要让这一层逐字可复现，就得把 agent 的动作**串行化**（或者引入一个全局的、
与真实耗时无关的确定性调度）。但并发正是这个仿真跑得动的前提：一轮几百个 agent，
串行化会把墙钟时间乘上并发数。

所以这是**取舍，不是对错**：换来的确定性和花掉的时间，谁更重要取决于用途。
对「要一份可复现的推演」来说是值得的；对「要一个跑得完的大规模仿真」来说不是。

**我们的立场是：这一层不承诺可复现，只承诺可检出** —— 能说清它是被什么决定的、
灵敏度有多高，比含糊地说一句「随机性」有用，也比假装能修好诚实。

## 5. 一个可以立刻落地的中间做法

如果短期内不打算动并发模型，至少可以**把不确定性摊开报**，而不是让它藏在
一份看起来确定的报告里：

* 同一份输入跑 N 次，报**均值与方差**，而不是报一次的数；
* 把每次运行里 `post_id` 的分配次序一并存下来，让两次运行**对得上账**。

这样「跑两次不一样」就从一个 bug 报告变成一条**已知边界**，
使用者也才知道该怎么读那份报告。

---

**复现说明**：上面第 2、3 节的两个数是离线量出来的，不发 LLM、不要 API key ——
用干跑（把每个 agent 的动作换成固定耗时）与真实事件循环的 `asyncio.gather` 组合，
量落库次序。需要的话我们可以在评论里补齐完整的最小复现脚本。
